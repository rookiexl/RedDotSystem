## 一句话理解

**红点运算单元是一个全局唯一、能算出一个整数的业务计数器。**

- 红点运算单元回答的是：**「这个红点该不该亮？数字是几？」**
- 红点名回答的是：**「这个红点显示在 UI 的哪个位置？由哪些单元汇总而来？」**

多个运算单元通过绑定组成一个红点名的计算规则；子红点绑定的单元会自动汇总到父红点。

## 核心概念

系统里有五个核心角色：

| 角色 | 职责 | 代码位置 |
| --- | --- | --- |
| `RedDotUnitInfo` | 红点运算单元的定义：名字、描述、计算函数、显示类型 | `Assets/RedDot/Runtime/RedDotUnitInfo.cs` |
| `RedDotInfo` | 红点名节点：保存当前红点名绑定的所有单元 | `Assets/RedDot/Runtime/RedDotInfo.cs` |
| `RedDotHandler` | 注册单元、监听业务事件、把单元标脏 | `Assets/RedDot/Runtime/RedDotHandler.cs` |
| `RedDotManager` | 调度计算、把变化传播给红点名、通知订阅者 | `Assets/RedDot/Runtime/RedDotManager.cs` |
| `RedDotWidget` | UI 视图：订阅红点名并渲染结果 | `Assets/RedDot/Unity/RedDotWidget.cs` |

关系可以概括为：

```text
RedDotInfo（红点名，树节点）
    │  1 : n
    ▼
RedDotUnitInfo（运算单元，最小计算因子）
    │
    └── Func<int> 计算函数

RedDotModel
    ├── 单元结果缓存：单元名 -> 当前值
    └── 反向索引：单元名 -> 受影响的红点名列表
```

红点名之间是树形关系，用 `|` 分隔父子层级，例如：

```text
MAIN_UI_MAIL
├── PUBLIC_MAIL
├── BATTLE_MAIL
└── OTHER_MAIL
```

对应的红点名为：

```text
MAIN_UI_MAIL
MAIN_UI_MAIL|PUBLIC_MAIL
MAIN_UI_MAIL|BATTLE_MAIL
MAIN_UI_MAIL|OTHER_MAIL
```

**运算单元不是树节点**。它只是挂在红点名上的「影响因素」。

## 运算单元的定义

`RedDotUnitInfo` 包含四个字段：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `RedDotUnit` | 单元名，全局唯一 | `NEW_BATTLE_MAIL_NUM` |
| `RedDotUnitDes` | 单元描述，调试用 | `新战斗邮件数` |
| `RedDotUnitCalculateFunc` | 计算函数，返回 `int` | `() => MailModel.Singleton.NewBattleMailNum` |
| `RedDotType` | 显示类型 | `RedDotType.NUMBER` |

定义位置：`Assets/RedDot/Runtime/RedDotUnitInfo.cs:18`。

### 计算函数约定

```csharp
Func<int> calculateFunc;
```

- 返回值 `> 0`：红点亮起，数字模式下显示该值。
- 返回值 `0` 或负数：红点不显示。
- 函数应当是一个**只读的 getter**，只读取 Model 状态，不要在里面做写操作或重逻辑。
- 返回值类型固定为 `int`，不支持字符串或复杂对象。

### 结果不存在单元里

单元对象只保存「怎么算」，不保存「算出来是多少」。  
结果统一缓存在 `RedDotModel.mRedDotUnitResultMap` 中：

- `GetRedDotUnitResult(unit)`：读缓存
- `SetRedDotUnitResult(unit, result)`：写缓存

见 `Assets/RedDot/Runtime/RedDotModel.cs:397` 和 `:412`。

### 单元与红点名的区别

| | 红点运算单元 | 红点名 |
| --- | --- | --- |
| 本质 | 一个业务计数器 | 一个 UI 显示位置 / 汇总节点 |
| 例子 | `NEW_BATTLE_MAIL_NUM` | `MAIN_UI_MAIL\|BATTLE_MAIL` |
| 是否有层级 | 没有 | 有，用 `\|` 表示父子 |
| 是否直接对应 UI | 不直接对应 | 直接对应 |
| 数量关系 | 一个单元可影响多个红点名 | 一个红点名可包含多个单元 |

## 注册与绑定

### 业务侧写法

以战斗邮件为例，处理器 `MailUIBattleMailRDH` 注册了两个单元：

```csharp
protected override void InitRedDotDatas()
{
    AddBindRedDotUnit(
        RedDotUnit.NEW_BATTLE_MAIL_NUM,
        "新战斗邮件数",
        CaculateNewBattleMailNum,
        RedDotType.NUMBER);

    AddBindRedDotUnit(
        RedDotUnit.BATTLE_MAIL_REWARD_NUM,
        "战斗邮件可领奖数",
        CaculateNewBattleMailRewardNum,
        RedDotType.NUMBER);
}
```

见 `Assets/Scripts/GameLogic/Module/Mail/RedDot/RedDotHandler/MailUIBattleMailRDH.cs:21`。

### `AddBindRedDotUnit` 内部做了什么

`AddBindRedDotUnit` 位于 `Assets/RedDot/Runtime/RedDotHandler.cs:75`，内部完成三件事：

1. **注册单元定义**  
   调用 `RedDotModel.AddRedDotUnitInfo`，把单元名、描述、计算函数、显示类型登记到全局。

2. **记录当前处理器的绑定关系**  
   把单元加入 `mBindRedDotUnitMap`，方便后续清理。

3. **记录当前节点的本地绑定**  
   调用 `RedDotInfo.AddRedDotUnit(redDotUnit, isRecursive)`。

### 延迟解析：父红点自动获得子单元

`RedDotInfo.AddRedDotUnit` 只记录当前节点的本地绑定，不再递归修改父节点：

```csharp
var redDotBindData = new RedDotUnitBindData();
redDotBindData.Init(redDotUnit, recusive);
mRedDotUnitBindDataMap.Add(redDotUnit, redDotBindData);

RedDotModel.Singleton.RebuildDerivedRedDotData();
```

`RedDotModel.RebuildDerivedRedDotData` 会遍历所有节点的本地绑定：

1. 本地单元先加入当前红点。
2. 递归绑定的单元再通过前缀树汇总到所有已注册父红点。
3. 最后重建 `mRedDotUnitNameMap` 反向索引。

因此绑定 `MAIN_UI_MAIL|BATTLE_MAIL` 的单元后，父红点 `MAIN_UI_MAIL`
会自动获得该单元；父红点不需要写「公共邮件 + 战斗邮件 + 其他邮件」的汇总逻辑。

### 反向索引：单元变了，该通知谁

统一重建父子关系时还会维护一张反向索引：

```text
mRedDotUnitNameMap: 单元名 -> 受影响的红点名列表
```

例如：

```text
NEW_BATTLE_MAIL_NUM
    -> [MAIN_UI_MAIL|BATTLE_MAIL, MAIN_UI_MAIL]
```

这张表在运行时非常关键：单元结果变化后，系统通过它反查需要刷新的红点名。

### 注册顺序

父红点和子红点的注册顺序不再影响汇总结果。  
子节点先注册时先保存本地绑定；父节点后注册后，模型会重新解析并补齐父级有效单元。

同一单元被多个子节点复用时，父节点只保留一份有效单元；移除其中一个子节点不会误删其他子节点仍在使用的汇总结果。

### 启动配置校验

`CompleteRegistration()` 完成父子关系解析后，默认只在 Editor 和 Development Build
执行配置校验，结果保存在 `RedDotInitializer.Singleton.LastValidationReport`。
Release Player 默认关闭，可通过 `EnableAutomaticValidation` 手动开启。

会检查：

- 重复注册的红点名、运算单元和本地绑定。
- 缺失父节点、空层级和空叶子节点。
- 引用了未定义运算单元的节点。
- 未绑定计算函数的运算单元。
- 未被任何节点使用的运算单元。

## 运行时计算流程

### 总览

```text
业务事件（例如收到新战斗邮件）
    │
    │ 处理器调用 MarkRedDotUnitDirty("NEW_BATTLE_MAIL_NUM")
    ▼
mDirtyRedDotUnitSet = { NEW_BATTLE_MAIL_NUM }
    │
    │ 只是标脏，不立刻计算
    │ 每 10 帧执行一次 CheckDirtyRedDotUnit()
    │ 每次最多处理 30 个脏单元
    ▼
DoRedDotUnitCaculate()
    │ 读旧值 -> 调计算函数 -> 得到新值 -> 写回缓存
    ▼
新值 != 旧值 ?
    │
    ├── 否：结束，不通知 UI
    │
    └── 是
         │
         ▼
    GetRedDotNamesByUnit() 反查受影响红点名
         -> [MAIN_UI_MAIL|BATTLE_MAIL, MAIN_UI_MAIL]
         │
         ▼
    TriggerRedDotNameUpdate() -> 生成 Snapshot -> 通知订阅者
         │
         ▼
    RedDotWidget.Render()：Result > 0 就显示
```

### 1. 业务事件只负责标脏

处理器监听业务事件，事件到来时调用：

```csharp
RedDotManager.Singleton.MarkRedDotUnitDirty(RedDotUnit.NEW_BATTLE_MAIL_NUM);
```

标脏接口位于 `Assets/RedDot/Runtime/RedDotManager.cs:350`，实现只有一个 `HashSet.Add`：

```csharp
public void MarkRedDotUnitDirty(string redDotUnit)
{
    mDirtyRedDotUnitSet.Add(redDotUnit);
}
```

所以同一帧内重复标脏不会产生重复计算。

### 2. 每 10 帧批量处理

`RedDotManager.Update` 位于 `Assets/RedDot/Runtime/RedDotManager.cs:294`：

```csharp
public void Update()
{
    mFramePassed++;
    if (mFramePassed >= DIRTY_UPDATE_INTERVAL_FRAME)
    {
        CheckDirtyRedDotUnit();
        mFramePassed = 0;
    }
}
```

两个限制：

- `DIRTY_UPDATE_INTERVAL_FRAME = 10`：每 10 帧检查一次。
- `CALCULATE_RED_DOT_UNIT_NUM_PER_FRAME = 30`：每次最多计算 30 个单元。

如果脏单元超过 30 个，剩余部分会留到下一次检查继续处理。最坏情况下，刷新延迟会随脏单元数量增加。

### 3. 执行单元计算

`DoRedDotUnitCaculate` 位于 `Assets/RedDot/Runtime/RedDotManager.cs:453`：

```csharp
private bool DoRedDotUnitCaculate(string redDotUnit)
{
    var preResult = RedDotModel.Singleton.GetRedDotUnitResult(redDotUnit);
    var redDotUnitFunc = RedDotModel.Singleton.GetRedDotUnitFunc(redDotUnit);
    var result = preResult;
    if (redDotUnitFunc != null)
    {
        try
        {
            result = redDotUnitFunc();
        }
        catch
        {
            // 保留最后一次有效结果，继续处理同批其他单元。
            return false;
        }
    }
    RedDotModel.Singleton.SetRedDotUnitResult(redDotUnit, result);
    return preResult != result;
}
```

关键点：

- 只有被标脏的单元才会执行计算函数。
- 计算前先读旧值，计算后写回缓存。
- 计算函数抛异常时保留最后一次有效结果，不阻断同批其他单元。
- 返回值为 `true` 表示结果发生变化，才需要通知红点名。

### 4. 结果变化后传播到红点名

`CheckDirtyRedDotUnit` 位于 `Assets/RedDot/Runtime/RedDotManager.cs:367`，核心流程：

1. 从脏集合中取出最多 30 个单元。
2. 逐个执行 `DoRedDotUnitCaculate`。
3. 如果结果变化，通过 `GetRedDotNamesByUnit` 找到所有受影响的红点名。
4. 把红点名加入待刷新集合。
5. 对每个待刷新红点名调用 `TriggerRedDotNameUpdate`。

`TriggerRedDotNameUpdate` 会生成最新快照并通知订阅者。  
每个订阅回调独立捕获异常，一个 UI 回调失败不会阻断其他订阅者或下一批脏单元。

### 5. 查询只读缓存，不触发计算

`GetRedDotNameResult` 位于 `Assets/RedDot/Runtime/RedDotManager.cs:163`，它只做两件事：

1. 遍历红点名绑定的单元列表。
2. 把每个单元的**缓存值**相加，并组合显示类型。

它**不会调用任何计算函数**。这就是为什么启动时需要先跑一次全量计算：

```csharp
RedDotManager.Singleton.MarkAllRedDotUnitDirty();
RedDotManager.Singleton.EvaluateAllDirtyNow();
```

见 `Assets/Scripts/GameLogic/Bootstrap/GameStartupPipeline.cs:63`。

`EvaluateAllDirtyNow` 会循环调用 `CheckDirtyRedDotUnit`，直到所有脏单元处理完毕，确保 UI 首帧拿到完整快照。

## 结果聚合与显示规则

### 红点结果 = 所有单元结果之和

```text
红点结果 = Σ（该红点名绑定的所有单元的缓存值）
```

例如：

```text
MAIN_UI_MAIL|BATTLE_MAIL
    ├── NEW_BATTLE_MAIL_NUM     = 3
    └── BATTLE_MAIL_REWARD_NUM  = 2

结果 = 3 + 2 = 5
```

### 显示类型 = 所有正结果单元的类型按位或

```text
显示类型 = OR（所有 result > 0 的单元的 RedDotType）
```

`RedDotType` 是一个 `[Flags]` 枚举，见 `Assets/RedDot/Runtime/RedDotType.cs:18`：

| 类型 | 值 | 显示 |
| --- | --- | --- |
| `RED` | `0x0001` | 纯红点 |
| `NUMBER` | `0x0002` | 数字红点 |
| `NEW` | `0x0004` | 新红点 |

组合示例：

- `NEW` + `NUMBER` = `NUMBER_NEW`
- `RED` + `NUMBER` = `RED_NUMBER`
- `RED` + `NUMBER` + `NEW` = `RED_NUMBER_NEW`

### 文本显示优先级

`RedDotUtilities.GetRedDotResultText` 位于 `Assets/RedDot/Runtime/RedDotUtilities.cs:63`：

| 条件 | 显示 |
| --- | --- |
| `result <= 0` | 不显示 |
| 类型包含 `NEW` | 显示「新」 |
| 类型包含 `NUMBER` | 显示具体数字 |
| 只有 `RED` | 只显示红点图片，不显示文本 |

也就是说，显示优先级为：

```text
NEW > NUMBER > RED
```

### UI 渲染

`RedDotWidget` 位于 `Assets/RedDot/Unity/RedDotWidget.cs:86`：

1. `OnEnable` 时订阅红点名。
2. 立即用 `GetSnapshot` 渲染一次当前缓存。
3. 调用 `RequestRefresh` 请求一次强制刷新。
4. 收到订阅回调后重新渲染。

```csharp
mSubscription = RedDotService.Provider.Subscribe(mRedDotName, OnRedDotRefresh);
Render(RedDotService.Provider.GetSnapshot(mRedDotName));
RedDotService.Provider.RequestRefresh(mRedDotName);
```

`RedDotSnapshot` 是传给视图的不可变结构：

```csharp
public readonly struct RedDotSnapshot
{
    public string RedDotName { get; }
    public int Result { get; }
    public RedDotType DisplayType { get; }
    public bool IsVisible => Result > 0;
    public bool IsValid => !string.IsNullOrEmpty(RedDotName);
}
```

## 完整示例：战斗邮件红点

### 红点树

```text
MAIN_UI_MAIL
├── MAIN_UI_MAIL|PUBLIC_MAIL
├── MAIN_UI_MAIL|BATTLE_MAIL
└── MAIN_UI_MAIL|OTHER_MAIL
```

定义见 `Assets/Scripts/GameLogic/RedDot/RedDotNames.cs:28` 和 `:67`。

### 战斗邮件红点绑定的单元

```csharp
AddBindRedDotUnit(
    RedDotUnit.NEW_BATTLE_MAIL_NUM,
    "新战斗邮件数",
    CaculateNewBattleMailNum,
    RedDotType.NUMBER);

AddBindRedDotUnit(
    RedDotUnit.BATTLE_MAIL_REWARD_NUM,
    "战斗邮件可领奖数",
    CaculateNewBattleMailRewardNum,
    RedDotType.NUMBER);
```

### 假设缓存值

| 单元 | 值 |
| --- | ---: |
| `NEW_PUBLIC_MAIL_NUM` | 1 |
| `PUBLIC_MAIL_REWARD_NUM` | 0 |
| `NEW_BATTLE_MAIL_NUM` | 3 |
| `BATTLE_MAIL_REWARD_NUM` | 2 |
| `NEW_OTHER_MAIL_NUM` | 4 |

### 结果

**战斗邮件页签：**

```text
3 + 2 = 5
```

显示「5」。

**主界面邮件入口：**

因为模型会派生父子汇总关系，`MAIN_UI_MAIL` 的单元列表已经包含三个子红点的全部单元：

```text
1 + 0 + 3 + 2 + 4 = 10
```

显示「10」。

代码里没有一行「公共 + 战斗 + 其他」的汇总逻辑，这是命名层级派生自动完成的。

### 一个业务语义提醒

运算单元是**独立维度**，不是去重后的实体数量。

如果一封邮件同时满足「新邮件」和「可领奖」，它会同时计入：

- `NEW_BATTLE_MAIL_NUM`
- `BATTLE_MAIL_REWARD_NUM`

父红点就会出现重复计数。  
如果业务要求去重，需要在计算函数内部自行处理，框架不会帮你合并。

## 为什么这样设计

### 1. 复用

一个单元可以被多个红点名引用，只定义一次。

例如 `WEARABLE_EQUIP_NUM` 可以同时影响：

- 装备界面红点
- 主界面装备入口红点

### 2. 父子自动汇总

子红点绑定一次单元，所有祖先红点自动获得该影响因素。  
新增一个子功能时，不需要回头修改父级汇总逻辑。

### 3. 性能可控

- 事件到来时只标脏，不立即计算。
- 每 10 帧批量处理。
- 每次最多计算 30 个单元。
- 结果缓存，未变化不通知 UI。

### 4. 逻辑与表现解耦

- 业务层：只负责「数据变了，标脏哪个单元」。
- 框架层：负责计算、聚合、传播。
- UI 层：只负责「订阅哪个红点名，怎么渲染」。

## 常见误区与设计约束

### 误区 1：把运算单元当成红点名

运算单元是「算什么」，红点名是「在哪显示、汇总谁」。  
一个单元可以服务多个红点名，一个红点名也可以包含多个单元。

### 误区 2：以为查询会实时计算

`GetRedDotNameResult` / `GetSnapshot` 只读缓存，不调用计算函数。  
计算只发生在脏单元被 `CheckDirtyRedDotUnit` 处理时。

### 误区 3：用负数表示「没有」

返回 `0` 即可隐藏红点。  
负数会参与求和，可能把其他单元的正数抵消掉。

### 误区 4：在计算函数里做写操作

计算函数应该是纯读取，例如：

```csharp
protected int CaculateWearableEquipNum()
{
    return EquipModel.Singleton.WearableEquipNum;
}
```

不要在里面刷新 UI、发事件或修改 Model。

### 误区 5：以为标脏会立刻刷新

标脏只是把单元加入集合。  
实际刷新发生在下一次 `Update` 检查（最多约 10 帧后）；脏单元过多时还会分批。

### 误区 6：忽略首帧缓存

启动时必须执行全量标脏和立即计算，否则 UI 首帧可能读到默认值 0：

```csharp
RedDotManager.Singleton.MarkAllRedDotUnitDirty();
RedDotManager.Singleton.EvaluateAllDirtyNow();
```

### 误区 7：认为父红点必须先注册

当前实现会先保存本地绑定，再由模型统一派生父子关系。  
父红点注册晚于子红点不会导致汇总缺失；但父红点最终仍然需要注册，否则不会产生对应父入口。

### 设计约束

| 约束 | 说明 |
| --- | --- |
| 聚合方式固定为求和 | 框架不支持取最大值、取最小值或自定义聚合；复杂逻辑需要封装在单个单元的计算函数里 |
| 单元结果是 `int` | 不支持字符串、列表或复杂对象 |
| 单元显示类型全局共享 | 同一个单元被多个红点名复用时，显示类型也共享；需要不同显示类型时应拆成不同单元 |
| 单元名全局唯一 | 重复注册会报错；动态单元需要用 ID 拼接避免冲突 |
| 只有结果变化才自动通知 | 需要强制刷新时使用 `ForceRefreshRedDotName` / `RequestRefresh` |

## 新增一个红点的步骤

### 1. 定义红点名

在 `Assets/Scripts/GameLogic/RedDot/RedDotNames.cs` 中定义，使用父名 + `|` 拼出层级：

```csharp
public const string MAIN_UI_MAIL = "MAIN_UI_MAIL";
public const string MAIL_UI_BATTLE_MAIL = MAIN_UI_MAIL + "|BATTLE_MAIL";
```

### 2. 定义运算单元名

在 `Assets/Scripts/GameLogic/RedDot/RedDotUnit.cs` 中定义：

```csharp
public const string NEW_BATTLE_MAIL_NUM = "NEW_BATTLE_MAIL_NUM";
```

### 3. 编写红点处理器

新建一个继承 `GameRedDotHandler` 的类：

```csharp
public class MailUIBattleMailRDH : GameRedDotHandler
{
    protected override void InitRedDotDatas()
    {
        AddBindRedDotUnit(
            RedDotUnit.NEW_BATTLE_MAIL_NUM,
            "新战斗邮件数",
            CaculateNewBattleMailNum,
            RedDotType.NUMBER);
    }

    protected override void AddAllEvents()
    {
        base.AddAllEvents();
        AddEvent(EventId.NewBattleMailNumUpdate, OnNewBattleMailNumUpdate);
    }

    private void OnNewBattleMailNumUpdate(object param)
    {
        RedDotManager.Singleton.MarkRedDotUnitDirty(RedDotUnit.NEW_BATTLE_MAIL_NUM);
    }

    private int CaculateNewBattleMailNum()
    {
        return MailModel.Singleton.NewBattleMailNum;
    }
}
```

### 4. 注册红点信息

在对应的 `FuncRDInitializer` 中注册：

```csharp
protected override void InitRedDotInfos()
{
    AddRedDotInfo<MailUIBattleMailRDH>(
        RedDotNames.MAIL_UI_BATTLE_MAIL,
        "邮件界面战斗邮件红点");
}
```

### 5. UI 绑定红点名

在 `RedDotWidget` 上设置红点名：

```csharp
widget.SetRedDotName(RedDotNames.MAIL_UI_BATTLE_MAIL);
```

Widget 会自动订阅、渲染，并在收到刷新通知时更新显示。

## 最后记住这句话

**运算单元是叶子上的计数器，红点名是树上的汇总节点。**

事件只负责把叶子标脏；`Update` 负责重算脏叶子；结果变化后沿反向索引通知对应的树节点；UI 最终显示的是节点上所有单元结果之和。
